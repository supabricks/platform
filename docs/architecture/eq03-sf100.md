## Capacity admission and first blocker

After user cleanup, `/data2` had 764 GiB available on 2026-10-08. That admits
generation. It is **not yet proof that the entire retained product workload fits**:
PostgreSQL data/indexes, pageserver/object history, safekeeper WAL, capture spool,
live and retained Delta roots, independent Spark input tables, outputs and spill
need a combined budget. The SF1 load retained about 21.3 GiB in its cell, but
blindly multiplying that by scale would mix fixed costs and historical growth.

[#213](https://github.com/supabricks/platform/issues/213) records the first
source-audit blocker: the incremental worker limits each generation to 1 GiB
and all retained roots to 4 GiB. Planning, rollover scheduling and Rust descriptor
validation independently enforce related bounds. A larger snapshot/export limit
does not enlarge incremental capacity. Compaction cannot solve an oversized live
set. The full SF100 load must not start with those defaults.

The baseline [admission receipt](tpcds-evidence/2026-10-08-sf100-admission/baseline.json)
reproduces the installed worker's rejection one byte above 1 GiB, the planning
rejection at that size, and the retention rejection one byte above 4 GiB. A
one-byte-below-1-GiB control succeeds. Reproduce with
`e2e/tpcds/storage_admission.py --release <installed-release> --output <fresh-json>`.
These are sparse-file accounting probes with zero allocated payload bytes, not
valid Delta data or performance tests. They establish the original limit without
wasting a large load and do not replace the real-data capacity slice.

The capacity slice must use an explicit, durable storage profile, preserve
existing defaults, and keep worker reservations, controller admission/rollover,
replay and historical descriptor validation consistent. File count, manifest
size, version count, worker RSS, per-run deadline and query limits remain
separate constraints. Existing 16 MiB compaction output files and 4,096-file
inventories also need admission analysis before choosing a larger byte limit.
Do not silently increase memory/timeouts or weaken retention/lease safety.

## Execution slices and evidence

1. Generate and validate the full SF100 input under the pinned generation
   profile. Preserve exact input inventory, timing and disk receipt.
2. Reproduce #213 using a bounded live set above 1 GiB. Add the explicit storage
   profile, verify exact old/new data and replay/rollover behavior, and record
   before/after elapsed time, RSS, retained bytes and write amplification.
3. Bind load/reference/verification receipts to SF100 scale and generation
   inventory. Remove SF1-only row-count assumptions through explicit workload
   admission, preserving legacy SF1 behavior. Budget total cell storage, WAL and
   history before the large load; retain stop/resume dispositions without
   retrying ambiguous COPY commits.
4. Load all 24 tables with continuous sync on. Retain per-table throughput,
   commit/publication lag, backlog, worker RSS, compaction and storage growth.
   Stop at the first admission/correctness failure and open an issue. Measure
   each fix separately before continuing qualification.
5. At a fixed final epoch, compare typed PostgreSQL and Delta contents exactly
   for all 24 tables, then run every one of the 103 pinned query statements.
   Generate the independent Spark 4.2 reference from the same SF100 files.
   Record each success, failure, timeout, memory/spill peak and result comparison.
   Long table/query work must remain within, or explicitly renew, its epoch and
   session leases.

The SF1 q39 oracle acceptance in #206 is bound to SF1 source groups and cannot
